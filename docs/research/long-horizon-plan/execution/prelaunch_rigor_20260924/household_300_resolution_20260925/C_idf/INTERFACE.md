# C building and AC interface — 300 roles

`building_300.json` is the frozen C geometry/weather/thermal manifest keyed by `cityrole-0001` through `cityrole-0300`. Its `idf_path` is an actual EnergyPlus 24.1 IDF. `source_idf_sha256`, `source_accdb_sha256`, `parent_idf_sha256`, `weather_epw_sha256`, and `idf_sha256` are checked by the builders/runners. `source_unit_audit_300.json`, `static_audit_300.json`, and `runtime_300.json` are separate source, geometry, and execution evidence. The modeled cases are synthetic; `physical_calibration=false` and `human_response_observed=false`.

## D device integration boundary

`FROZEN_INPUTS.json` pins the C base manifest and all 300 IDF/EPW pairs. D owns the B device-count, appliance and ten-day occupancy bindings. Each record lists `household_owned_zones`, `ac_controllable_zones`, and `controls.zone_control_schedules`; the latter gives the `EB_Cooling_i` schedule and EnergyPlus API actuator key for each potential zone.

`operational_ac_idf.py` supplies the pure function `operational_body(building, assignment)` as an optional D adapter. Pass a C building record and an assignment with matching `role_id`, `building_idf_sha256`, and unique `assigned_zone_names` drawn from `ac_controllable_zones`. It sets C candidate cooling schedules to 40°C outside the assigned zones (28°C by default) and also sets each unassigned zone's IdealLoads availability to zero. It replaces C's broad technical EMS meter with a meter for only the assigned zones, including a zero meter when the list is empty. The function rejects unrelated EMS objects rather than removing them. `zero_ac_probe.json` records a one-day EnergyPlus case with seven hard-off candidate zones, zero selected-zone cooling thermal energy and zero AC proxy electricity. This adapter does not select household devices or define ten-day routines.

D should use `Cooling:Electricity` or `EB Selected Household AC Proxy Electricity Energy` for this experimental AC proxy. EnergyPlus facility electricity also contains original source background zones and must not be labeled household device load. `terraced_room_function_13.json` verifies the 13 converted terraced source units' per-zone functions from the matching DeST `ROOM` and `ROOM_TYPE_DATA` tables; for each, the four bedroom AC candidates are `1-N-9`, `2-N-9`, `2-N-10`, `2-N-12`, with `1-N-8` and `2-N-11` as living-room alternatives. The experimental fifth room `1-N-7` has no IdealLoads system and cannot be controlled through this AC interface. Shared homes may only assign this household's private rooms. `api_multizone_probe.json` checks one zone's API actuator without changing the other six.

## Geometry semantics

The A field `dwelling.design_total_building_area_m2` is H6-like **building area**. Independent homes use an experimental net-area ratio of `1/1.33`; this is an inverse of the census fallback for unknown building area, not a measured conversion for these households. Shared homes use a separate experimental ratio of 0.95, because H6 here means the household's private rooms plus an equal allocation of declared common zones, rather than an entire flat. `shared_layout_27.json` recomputes every private + allocated common = modeled household share identity from the final IDF and records source-floor-zone bounding dimensions. `shared_plans/` contains 27 geometry-derived SVG plans, with private, common, and other-resident zones distinguished. Bounding boxes are upper bounds on clear room dimensions; neither furniture placement nor building-code compliance has been established.

`cityrole-0020` has a 4.79m² smaller private room with a floor-zone bounding box of 1.864×2.741m. This remains a tight experimental living arrangement for its three-person household with two private rooms. A 5cm raster of the **actual floor polygons** found room to place a 2.0×0.9m single-bed footprint beside a 0.6m strip in both rooms. `shared_0020_sleeping_check.json` records the experimental arrangement of one single bed in the secondary bedroom and a two-level bunk for two people in the master bedroom. Door access, furnishings, bunk headroom and human acceptability remain unverified. The other 26 shared cases' smallest individual private room is at least 6m². For `cityrole-0004`, private area is 6.392m² and allocated common is 1.208m², summing to 7.6m² modeled net share for an 8m² H6-like building-area share. The entire modeled source unit is 35.783m² net; that full unit must not be charged to the one role.

## Energy and evidence boundaries

The base IDF retains the DeST converted IdealLoads systems and source schedules. `EB_Cooling_i` controls each potential household zone. EMS reads each selected zone's *thermal* cooling and divides it by an experimental fixed COP of 3 to create a metered **electricity proxy**. This is not a measured AC, fan-inclusive heat pump, calibrated capacity or part-load model. The broad base IDF cools every potential zone; D must restrict active zones before household device scenarios. Other B devices and role-specific occupancy schedules are D integration work and are not represented by C's standalone base run.

`runtime_300.json` certifies that all 300 base IDFs completed a one-day July 15 EnergyPlus run with no Severe/Fatal error and exact EMS meter-to-zone proxy accounting. Warnings remain: source ground temperatures outside EnergyPlus's suggested range, missing type limits on converted source schedules, interspace surfaces in the same space, and unused constructions. These passes establish execution and accounting, not physical or behavioral validity. `paired_ac_five_modes.json` contains five same-IDF/weather 24→28°C event tests, all with positive proxy reduction. `api_multizone_probe.json` checks seven distinct actuator handles and a one-zone treatment. `sensitivity_8.json` contains eight actual model parameter runs.
