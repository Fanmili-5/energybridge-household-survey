# 最近修改后的链路审计

> 历史记录，保留当时的测试结果和设计依据。项目使用说明见[文档目录](README.md)。

审计基线：`cbbe3b5`；UI v6.16 / paired v3.6。2026-09-14。

目的：真人填写家庭信息，运行固定 EB 的 no_dr / agent 与 EP，收集家庭代表的接受/拒绝、四项小数评分及原因，交付可追溯数据。保持不变、负收益和原生技术回退样本；不能用方案是否理想来筛选数据。本轮是检查与问题定位，没有修改线上策略、用户答案、初始状态或历史结果。

## 结论

运行与保存链路通过当前测试，但还不能把当前展示数据直接当作“用户实际看到的信息”的精确记录。优先修复下面前三项，再冻结正式采集展示协议。其余是已经存在的模拟假设与跨天评价口径，需要明确记录；不应通过删时间条或臆造结果处理。

## 类似默认值的检查

这些不是全部需要新增问卷题目，但需要保持来源明确：

- EV 容量/每天行驶耗电、洗衣等额定功率、热水器设备参数来自固定设备模型；目标电量和使用时间由问卷覆盖。
- 在家人数是问卷映射；未询问的22:00—08:00使用在家比例1，部分/不固定时段使用0.5。代码已有解释字段，不能称实测作息。
- 房屋与天气是登记资源匹配，并非实测家庭住宅。原生供暖设定仍为20℃；可调整空调设定主要指制冷。全年日期可运行，不等于冬夏控制可调程度相同。
- 热水服务目前报告的是EP水箱温度，未冒充真实出水温度。`40℃ 待机`来自设定值判断，不能据此推断零耗电；可进一步缩为40℃以避免标签歧义。
- 两路为从仿真起点独立运行的 no_dr / agent，不强制 VPP 前轨迹相同。不能表述为“仅事件期间变化的因果差值”。

## 验证结果

1. `EPLUS_ROOT=/Applications/EnergyPlus-24-1-0 EB_TEST_NATIVE_EP=1 .venv/bin/python scripts/test_offline.py`：202项通过，75.988秒，含真实EP、固定模型回复，外部网络被测试框架禁止，付费API调用0。首次漏配EPLUS_ROOT的运行有2项找不到pyenergyplus；正确配置后完整重跑通过，未将环境错误记为产品缺陷。
2. `node scripts/test_plan_view.js`：跨日坐标、连续运行首尾、内部温度分段保留、停机间隔不合并、源数据不变等检查通过。
3. 线上25项HTTP、管理员隔离和无效验证码拒绝检查通过。当前仍是engineering模式；没有发起有效生成，也没有提交真人评分。
4. 热水日序与次日任务为小型诊断构造，只证明对应选择逻辑，不冒充新的真实家庭仿真或模型表现。
5. 本轮没有进行真实API高并发负载测试，不能由这些结果承诺50人同时生成的延迟或可用性。

## 修复与验收顺序

1. 统一实际展示快照、评分时页面版本与导出；证明未显示的说明不进入默认训练输入，旧评分版本缺失不会被伪造补齐。
2. 增加真实结束/比较截断区别；证明仍运行到截止的空调不会被描述为已关闭。
3. 对齐跨日任务与服务需求实例；覆盖首日凌晨、次日凌晨、真正跨夜、日常重复任务及观察截止边界。
4. 单列并保存模型补入的初始状态与设备参数。保留现有EB策略和真实输出，不为让两方案差异更明显而修改结果。
5. 再决定人民币情境电价方案；新条件用新版本，历史数据保持原单位。
