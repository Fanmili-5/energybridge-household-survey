# 全年随机日期（问卷 v4.1）

目的：真人家庭资料 → 原 EB 日常对照 / 规划与 EP 仿真 → 真人接受/拒绝、四项评分与原因 → 家庭 role-play SFT 候选。日期随机用于增加情境覆盖，不修改原 EB 策略或制造评价标签。

## 实际流程

1. 打开问卷时，服务端为浏览器会话抽定全年365天中的一天，页面先显示月份、日期和季节。每一天概率1/365；刷新不会重抽。使用2007非闰年实验日历，与已有EPW接口一致；不是2007某一天的历史实测天气。
2. 基本家庭信息照实填写；习惯和室温偏好按指定月份填写。住房信息继续匹配已审核的地区站点和住宅原型。月份季节仅是日历标注，实际气象来自所选站点，不把南方冬季自动视为寒冷。
3. 保存原始回答、问卷快照和独立的 `questionnaire_context`。后者是系统分配信息，不伪装成用户回答。保存请求必须与服务端已分配情境哈希一致。
4. 生成任务使用家庭回执中已固定的日期；VPP仍按原事件采样规则生成。先运行当天 `no_dr`；正常结束、无严重错误、时间序列完整后才运行 `agent`。不新增模型评价筛选。对照失败记录为技术失败，保留家庭资料，不调用规划模型、不重抽日期。
5. 两份方案使用同一日期/EPW/住宅。规划结果即使节省不明显或采用原生回退，只要技术上完成，仍可由真人评价。没有用评分或预计接受率筛选日期。

## 保存证据

- `/api/session.questionnaire_context`：版本、抽样标识、日期、日历季节、概率、来源、提示文本、哈希；不包含会话凭证。
- 家庭回执/`household_record.json.questionnaire_context`：冻结答题情境；`questionnaire_submission.json` 和 `request.json.scenario` 同步保存。
- `simulation_environment.json.date_sampling`：站点当天温度统计、概率、冻结上下文、逐案例验证政策。原始记录中的 `pending_case_baseline` 保留，不事后覆盖。
- `date_validation.json`：实际对照仿真通过或失败、日期、IDF/天气哈希；失败时明确 `planning_started=false`。成功结果引用该文件哈希。计算端归档回传包含此文件。
- SFT候选继续保存家庭资料、同一天两份方案、实际展示上下文和真人反馈；只有失败任务没有人为补造标签。

## 兼容与边界

- 原作者供暖目标20℃、制冷温度规划及控制流程不改。问卷明确空调温度题是制冷温度，不收集一个未接入的可调供暖设定。
- v4.0夏季原记录与快照保留；恢复成新问卷时需重填季节相关习惯，保留人口/住房等基本事实。旧工程直接调用及历史请求仍保留原夏季规则，不重新解释旧标签。
- 全国资源组合此前主要在三个夏季日验证过。现在允许其余日期逐案例真实验证，**不能声称全年每一天×所有住宅均已验证**。失败率需按地区、日期和房型报告，以免技术失败造成样本覆盖偏差。
- 本次没有更改采集模式、收费API配置、并发或登录规则；演示数据继续标为工程测试。跨浏览器不保证是不同家庭。
- EPW是典型年；建筑材料/HVAC为研究近似，价格仍为原EB统一天津权重。全年情境不等于全国真实住宅供暖系统已逐一校准。

## 验证

真实EP验证：北京冬/春/秋日常对照；北京冬季完整配对、反馈和SFT记录（模型用固定离线测试响应）；既有夏季区域配对回归。外部网络在测试程序中被禁止，无付费模型调用。

后端测试另覆盖：全年月份/365天覆盖、会话稳定、日期篡改拒绝、保存/任务日期一致、失败不调用agent、50个家庭并发保存与队列限额。浏览器检查确认抽定日期在填写前可见，刷新后日期与草稿保持。
