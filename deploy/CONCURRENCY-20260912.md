## 后续 24／32 并发验证

测试配额为 32 核 CPU、16 GiB 内存。每档 96 次同一合成家庭的原生日常仿真，重复三轮并交替测试顺序，共 864 次均成功、设备端口完整、用电量一致，没有网络或模型调用。

| EP 并发 | 每批 96 次耗时中位数 | 三轮耗时范围 | 进程 RSS 峰值 |
|---:|---:|---:|---:|
| 16 | 7.45 秒 | 6.78–7.51 秒 | 4.29 GiB |
| 24 | 5.05 秒 | 4.98–5.33 秒 | 6.35 GiB |
| 32 | 4.48 秒 | 4.10–4.81 秒 | 8.45 GiB |

32 相比 16 的纯 EP 吞吐量按批次中位数提高约 66%；相比 24 提高约 13%。内存仍有空间，但边际收益已减小。

再用独立数据库、独立 SSH 转发对 **任务32／EP32／API4** 运行 50 份突发提交：

- 50/50 完成，云端活动任务峰值32，整批84.29秒；没有错误或缺失哈希，没有真人标签。
- 云端探针及工作进程 RSS 峰值964.65 MiB。学校采样任务峰值12、EP名额峰值9、API名额峰值4，工作进程峰值2729.59 MiB；完整链路并未持续填满32个学校任务名额。
- 回传压缩包共60,399,833字节；仍为400次固定模型替身回复，收费调用为0。
- 上一轮16任务为99.17秒，本轮约缩短15%。两次完整链路各运行一轮，网络等因素没有完全控制，不能将差值解释为稳定提速保证。

根据纯 EP 和配对链路结果，当前配置提高到任务32／EP32／CPU配额32核，内存上限16GiB、API4、relay64和总在途64保持。只调整 EP 名额不会绕过 cloud worker、school slots 或 CPU 配额，三处需要一起配置。实际模型等待仍可能成为主要限制，600秒执行期限包含等待模型名额的时间。

## 随扩容修正

- 网站 CLI 支持 1–32 个 worker，计算端也限制在此范围；原生 EB 规划逻辑未改变。
- 计算 HTTP 和 API relay 接收队列均为 128。SDK 的空闲连接不再轻易耗尽原来的 8 个 relay 连接名额；relay 仍只允许指定 API 域名的 TLS 透传。
- 学校执行期限 600 秒，远程调用期限 660 秒，云端 worker 期限 720 秒；队列等待上限 600 秒。这些是故障上限，不是预计耗时。
- 运行容量两端一致，等待保留在阿里云持久队列；相同逻辑任务的重传仍复用固定远端 ID，不重复启动付费规划。
- 仍需 Mac 在线维持 SSH 路由。API 请求配额与 TCP 连接配额分别控制。
