# 有限参数敏感性验证

范围仅为第二条线。线上问卷、受访记录与 1000 户主仿真不参与。

## 两类联合与冲突的准确含义

`joint_family_limit=2` 是当前候选枚举的工程上限：联合两个不同候选族，并非最多改两台设备。洗衣候选携带独立烘干后继，所以洗衣＋EV 可改洗衣机、烘干机与 EV 三台。当前不枚举三族以上，也不枚举同族两台 AC。论文与设备物理均不推出“两类足够”；该数值是控制有限搜索规模的人工设定，构成覆盖边界。五族各十个变体时，两族乘积为 1000，而任意非空组合为 11^5−1=161050；这只是组合计数示例，不是本实验实际候选数。

静态冲突检查包括：原任务/操作/设备/人员身份与已发生部分保持不变；操作人有权限且在真实空闲窗口内；同一个人不能同时操作；非 EV 手动操作按房间容量一的项目资源约定互斥；已有预约不得占用；装载、完整程序、取出、最大等待、机器开放时段、占用区间与洗后取出再烘干的前后关系满足。温控与 EV 还检查设备边界、控制许可、原连接及预计剩余补能。

房间容量一是保守人工设定。上述检查没有实现住宅总回路功率/断路器容量的动态联合约束，也不构成所有设备热耦合的静态证明；热状态、SOC 与服务后果须由同环境配对仿真回读。不可将“静态通过”写成“所有后果保证成功”。

## 预先固定的实验

完整计划在 `examples/sensitivity/plan.json`，实现为 `sensitivity.py`。衣物量 0.6/1.2/1.8 kg、洗衣时长 40/60/80 min、热水需求倍率 0.5/1/1.5、占用制冷设定 25/26/27°C、EV 到家时刻 −30/0/+30 min，均为项目选定的扰动水平，不是论文原值或实测人群范围。EV 改动同时移动驾驶人离家/在家日历边界，保留晚餐、洗浴等固定活动。

生成层：中心点、十个单因素改动、32 个五因素二水平全组合，加上水箱死区 1/4°C、零衣物、容量 5 kg 与超容量 5.1 kg、零热水、没有插枪操作人、三档攒满再洗以及两组耦合压力，共 55 设置×3 示例家庭。保留所有未满足需求及残余衣物。独立检查完整周期、人员/手动房间互斥、真实空闲、前后与等待约束、批次容量、衣物质量守恒和 A 不读取 B 信息。全组合报告有限主效应与二因素乘积符号对比；包含失败设置，不作概率分布、统计显著性或全局 Sobol 敏感度推断。

方法依据是 [NIST 二水平全因子设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri333.htm)：全组合可以显露单因素检查漏掉的交互。32 个角点在此只用于成本较低的生成检查；物理层仅为预先固定的 20 个跟进案例，不能声称已验证所有物理交互。

物理层：3 个中心家庭、五因素各两端、两个水箱死区、零衣物、超容量、攒满再洗和两组压力。每个可行输入重新绑定设备/需求、生成完整日历 A、重新运行 EnergyPlus A=A 基线并通过准入；随后用新的完整 A 轨迹识别机会和生成 B。禁止修改旧 A 的温度/SOC 状态冒充新参数下的物理结果。每例最多四个引擎臂，共最多 80 臂；这些是 3 个合成家庭的参数案例，不能写成 20 个独立实测家庭。

B 面板预先固定为家庭洗衣＋EV、单间 AC＋水箱、共享住房洗碗机＋水箱。仅在该面板、shift_chain、制冷轴与 aligned 方向中选静态通过的候选，优先 A 机制支持子项数，然后接近预定剂量（程序 +30min、EV 暂停 60min、温控 1°C×20min），最后稳定 ID。记录实际剂量与窗口，因此这是固定规则随 A 调整的 B，并非每例完全相同的控制波形。不存在对应面板时不换成其他设备；不依据 B 节能、响应或成功结果重选。全部候选的冲突与不可用原因保留在原始证据中。

当前程序采用整周期定功率、每日服务或攒满批次的显式习惯。每日服务且低于容量时，衣物量变化可以只改变服务量而不改变周期数/电量。这是模型假设，不能据此声称真实洗衣能耗对负载不敏感；需与攒满再洗和容量边界共同解释。

## 复现

```sh
python -B -m unittest benchmark.ab_generation.test_sensitivity
python -B -m benchmark.ab_generation.sensitivity screen --out /tmp/eb-sensitivity-screen
python -B -m benchmark.ab_generation.sensitivity physics --energyplus-dir /Applications/EnergyPlus-24-1-0 --out /tmp/eb-sensitivity-physics
```

输出目录必须不存在。计划先于结果落盘，每例 B 选择先于对应 B 执行落盘，输入、代码、引擎、天气和证据均绑定哈希；引擎错误中止并保留证据，不补抽案例。A 需求未满足、A 物理服务不足、指定联合不可用与 B 服务失败分别记录。生成完整性通过、A 全部可行和 B 全部成功是三个不同判断。

## 本轮结果与适用边界

- 生成 165 例：162 个完整 A；3 个无人插枪边界的 A 保留为 `needs_unserved`，每个完整 153 天日历有 109 次插枪需求未满足。8 类独立完整性检查全部通过。不能把未满足需求删掉后报告 100% 可行。
- 物理 20 例全部入账，60 引擎臂：20 组重新生成的 A=A 身份基线；10 个指定面板无可行联合；10 个执行 B，其中 9 个通过服务检查，1 个违反独立舒适要求。全部 A=A 与配对中重跑 A 的原生通道误差为 0。
- 执行的 10 个 B 全部目标资产有可观测变化；26 个 A 支持的资产出现次数中无无响应项。只有 8 条不同的 `(case_id, native_B_trace)`，重复来自日洗定周期假设，不能冒充独立家庭或十种独立行为。10 个无联合机会的案例单列，不能从分母消失。
- 日洗模式：0.6/1.2/1.8 kg 都是 153 次洗衣、76.5 kWh；攒满模式则为 18/36/55 次，残余衣物为 1.8/3.6/0.4 kg；超过 5 kg 容量后的 5.1 kg 日需求被拆为 306 次完整周期。这暴露出轻载日洗与整周期定功率的建模假设，尚无真实负载能耗校准。
- 共享住房热水需求倍率 0.5/1/1.5，A 的 24h 水箱用电为 2.706/4.563/6.035 kWh；单间制冷设定 25/26/27°C，A 的冷却盘管用电为 3.848/3.298/2.736 kWh。EV 到家时刻 ±30min 保持同一出行电量，充电/操作时刻按真实连接变化。
- 水箱死区 1/2/4°C 下，固定晚间事件的指定洗碗＋水箱联合只在 1°C 时可用；2/4°C 的 A 事件窗没有向下减载的水箱工作余量。不是“安装水箱就一定可调”。
- 40min 洗衣下所有枚举位移均触发操作时间或人双重占用；超容量两批下则出现设备占用、机器开放时段等冲突。零衣物/攒满模式在指定日无洗衣任务时不编造洗衣机会。这些是当前有限网格和固定其他任务下的不可用，不是所有可能调度均无解的证明。
- 27°C 温控案例的 B 将占用制冷阈值上调 1°C 后，独立 18–28°C 舒适带外出现 10min、0.347°C·min；A 为零。保留为“有响应但服务受损”的样本，不能解释为用户必然拒绝。

因此本轮支持“已检验范围内，需求/周期/资源约束保持完整，机会与后果随条件变化可追溯”；不支持“所有参数下 B 都可行或成功”“两族覆盖所有联合情况”或“模型已完成真实人群校准”。10 个指定面板不可用也不等于没有任何单设备或其他面板 B。

公开汇总与逐例记录见 `validation/sensitivity/{SCREEN,PHYSICAL,CHECKS}.json`。原始 A、全候选（含冲突）、输入、选择收据、IDF、SQL、原生轨迹与引擎日志在本地原始证据归档保留，哈希及源码对应见 `validation/sensitivity/RECEIPT.json`。完整原始归档未宣称已上传 GitHub；公开仓库提供输入与复现命令。分析命令：

```sh
python -B -m benchmark.ab_generation.validation.sensitivity.analyze --screen-root /tmp/eb-sensitivity-screen --physical-root /tmp/eb-sensitivity-physics --out /tmp/eb-sensitivity-analysis
```
